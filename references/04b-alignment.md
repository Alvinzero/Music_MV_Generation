# 字幕对齐：只有一条流程，一套算法，一道硬门槛

> 字幕早半拍晚半拍，观众一眼就出戏。这一步决定成片"像不像专业剪的"。

**2026-10-22 重写**：原来的三套入口、两套参数已经合并。
不管手上是官方时间戳、歌词表还是烧好的 ASS，都走同一条链路、同一个算法、同一道 0.3s 门槛。

---

## 一、一条流程，三种输入

```
                  ┌─ 官方/TTS 时间戳（也要校准，不是免检）
song.m4a ──┐      ├─ 歌词表（只有文本 + 大致起止）
           ├──────┤
           │      └─ 已烧录的 ASS（只改 Start）
           ▼
   align_core.analyze()       ← 唯一前端：HPSS 去鼓 → 250–4200Hz → 4ms → 局部归一
           │
           ▼
   align_subs.py              ← 唯一入口：--lines 或 --ass
           │
           ├──▶ lines_sync.json / subs_sync.ass（校准结果）
           └──▶ sync_report.json（逐字偏差 + 置信度 + 门槛结论）
```

```bash
# A. 文本 → 逐字时间
python scripts/align_subs.py --audio song.m4a --lines out/lines.json \
    --out out/lines_sync.json --report out/sync_report.json --max-err 0.30 --strict

# B. 已烧录的 ASS → 只改 Start
python scripts/align_subs.py --audio song.m4a --ass out/subs.ass \
    --out out/subs_sync.ass --report out/sync_report.json --max-err 0.30 --strict
```

> **"有官方时间戳就不用校准"是错的。** 官方表也会整句晚 0.05–0.4s（实测过），
> 而且不同平台导出的表起点不一致。校准只花 8 秒，收益是把"差不多"变成"可测量"。
> 校准后 `delta` 就是"官方比实测晚/早多少"——超过 0.3s 的句子会被单独列出来。

## 二、唯一的一套算法（参数不许在别处再写一遍）

全部常量集中在 `scripts/align_core.py`，改那里等于改全链路。

| 环节 | 参数 | 为什么是它 |
|---|---|---|
| 采样 | 16 kHz 单声道 | 人声主区在 4kHz 以下，够了且快 |
| 帧 | NFFT 512 / HOP 64（**4ms**） | 10ms 步长会丢 1–2 帧的精度，字幕能感觉到 |
| 去鼓 | **HPSS**：频率方向中位 → 谐波 | 军鼓每一下都是强峰，不去掉会被当成字头 |
| 频带 | **250–4200 Hz** | 人声基频与共振峰都在内；再窄会丢辅音 |
| 变换 | `log1p(harm×12)` → 正向谱通量 | 压动态，让弱音节也能出峰 |
| 归一 | 1.5s 滑动中位相减 | 前奏与副歌的峰才可比，否则副歌永远赢 |
| 取峰 | 阈值 **0.10**、间隔 **45ms** | 实测这组在中文流行歌上最稳 |
| 对齐 | 句级位移搜索 ±0.6s + 句内 DP | DP 的转移代价必须含"间隔偏离惩罚" |
| 铺开 | 普通句 70%、大词句 52% | 剩下 30% 让整句立着，句末不拖 |

**为什么不再保留两套**：之前生成期用 250–3200Hz/10ms、修复期用 250–4200Hz/4ms，
同一句在两处会给出不同答案，而且没人知道哪个对。现在只有一套，误差来源也只剩一个。

## 三、硬门槛：逐字 ≤0.3s

`--max-err 0.30 --strict`：任何一个字超了，进程返回 2，不会静默过关。

### 0.3s 量的是什么（必须说清楚）

没有真值音频时，**"和标准答案的差"是测不出来的**。所以这里量两个东西：

| 指标 | 定义 | 用途 |
|---|---|---|
| `err`（门槛用） | 该字的时刻 → 本句**可信起音**的最近距离 | 判"有没有落在真实音节上" |
| `err_alt`（参考用） | DP 与贪心两套估计对同一个字的分歧 | 判"这个字到底对在哪个音上，是否含糊" |

- **可信起音**的阈值是自适应的：`0.55 × 本句中位峰强`。这首歌普通音节只有 0.15–0.25，
  用固定 0.30 会把正常字全判成错（实测过一次，30/36 句全红）。
- `err_alt > 0.3s` 的字进"人工复核队列"，但不判失败——它是"两种合理算法打架"，不是"一定错了"。

### 置信度分级

| 级别 | 条件 | 怎么处理 |
|---|---|---|
| **A** | `max_err ≤ 0.15` 且弱起音 ≤10% | 直接用 |
| **B** | `max_err ≤ 0.30` 且弱起音 ≤25% | 抽两帧听一下 |
| **C** | 超 0.30，或弱起音 >25% | **必须人工复核**，脚本会逐条列出 |

> ⚠️ **分层字幕（辉光层 + 实字层）只对齐实字层**，再把同样的位移套到另一层。
> 混在一起对齐会让两层分到不同的峰上（实测错到 1.22s，详见 `08-pitfalls.md` 第 24 条）。
> 而且这种错**能通过 0.3s 门槛**——每个字都落在起音上，只是落在了不同的起音。

### 本片实测（36 句 / 278 字，《无人知晓的我》）

```
偏差：中位 0.038s  p95 0.268s  最大 0.384s（门槛 0.30s）
两种方法分歧 >0.3s 的字：4 个（2 句）
A级 25 句 / C级 2 句 → 34/36 句过门槛
```

C 级两句：`那些欲言又止低头沉默`（0.304s）、`有些话不知道要怎么说`（0.384s）——
都是 10 字长句里的拖腔位置，**交给耳朵听，不要硬调参数**。

同一套算法跑已烧录的 ASS（568 字）：中位 0.000s、p95 0.273s、最大 0.284s，通过。

## 四、人工复核只有一件事：听那两句

脚本给不出"对/错"，只给"可疑"。C 级的处理流程：

1. 抽该句起止前后 0.5s 的音频，看波形/听一遍
2. 对照 `sync_report.json` 里逐字的 `t` 和 `peak`
3. 明显错的，直接改 `lines_sync.json` 里的 `times[]`（**改数据，不改脚本参数**）
4. 改完重跑 `align_subs` 只会覆盖正确的字——所以手动改过的句子要记在 `out/sync_manual.json`

**不要为了让它变绿去调阈值。** 门槛的作用是拦住不合格，不是逼你放水。

## 五、回流：校准结果要写回去

这是之前漏掉的一环——改完 ASS 就结束，`lines.json` 还是旧时间，下次重做又回到错的起点。

| 产物 | 用途 |
|---|---|
| `lines_sync.json` | **新的真源**：带 `times`/`start_fit`/`delta`/`win`/`grade`，下游 `make_subs` 直接吃 |
| `subs_sync.ass` | ASS 路线的结果，只改了 Start，其余字节原样 |
| `sync_report.json` | 逐字偏差 + 分级，出错时第一个看它 |

**规矩：一旦跑过 `align_subs`，后面所有步骤都引用 `lines_sync.json`，不再碰原始 `lines.json`。**
原始表只作为"输入记录"存档，便于追查 `delta` 是从哪来的。

## 六、唱歌 ≠ 说话（为什么不用 WhisperX 那类）

语音模型在唱歌上会退化，原因很具体：

- 基频大幅滑动（一个字跨五度），音素边界被拉糊
- 拖腔把字长拉 3–5 倍，模型没见过这种时长
- **伴奏压着人声**：鼓和贝斯在 250–3200Hz 有强能量，和辅音同频段

所以正确顺序永远是 `解码 → 去鼓（HPSS 或 Demucs）→ 只在人声上取峰`。
有 Demucs 更好：

```bash
python -m demucs --two-stems=vocals -n htdemucs -o out/stems song.m4a
# 之后把 --audio 换成 out/stems/htdemucs/song/vocals.wav
```

`align_core` 不检查你传的是不是人声轨——**这是调用方的责任**。传混音也能跑，
只是偏差会大一档（句起点标准差 0.415s vs 0.1s 量级）。

## 六之二、有官方 TTML 时：优先用官方骨架，不要用能量峰重排（2026-10-24 实测）

《说好不哭》这首歌踩过一个大坑，值得单列。

### 6.2.1 官方 TTML 是逐字标注，粒度最细

amll-ttml-db（`github.com/Steve-xmh/amll-ttml-db`）里的 TTML 是**每字一个 span**，
带 `begin`/`end`：

```xml
<span begin="00:26.510" end="00:26.740">没</span>
<span begin="00:26.740" end="00:26.930">有</span>
```

这比任何能量峰估计都可靠。**能拿到官方 TTML，就不要重排整条时间轴。**

### 6.2.2 先证同源，再谈校准

拿到官方 TTML 第一件事不是"用不用"，是**验证它和手上的音轨是不是同一条录音**。
验证方法只有一个可靠的：**逐句首尾字直接核对音轨上的强起音**。

```python
for 每句:
    首字官方时间 → 音轨上最近的强起音，差多少
```

《说好不哭》实测（d=0）：

| 句 | 官方首字 | 音轨强起音 | 差 |
|---|---|---|---|
| 不是我的错 是你要走 | 71.930 | 71.925 | 0.005 |
| 挽留的话却没有说 | 82.240 | 82.220 | 0.020 |
| 说好不哭让我走 | 94.830 | 94.825 | 0.005 |

→ 同一条录音，零偏移，可以直接用。

> ⚠️ **不要用"命中计数"这种离散指标扫偏移**。
> 本次先用「≤0.12s 命中数」扫出 d=−0.065（命中 99/294），
> 换成首尾字直接核对后 d=0 —— 离散计数被量化带偏了 65ms。
> **连续量（直接距离）比离散计数（命中数）可靠。**

### 6.2.3 官方 TTML 的坑：官方把多句合并成一句

官方 `<p>` 段数常常少于本地拆句数（37 句 vs 30 段）。
**不要按段号对应**，要用字符级 diff：

```python
difflib.SequenceMatcher(None, 本地字串, 官方字串, autojunk=False).get_opcodes()
# tag == "equal" 的块 → 建立逐字映射
```

本次 294/294 字全部对应上。

### 6.2.4 拖腔会让"句内第一个能量峰"当锚点

上一版 `place_line()` 用「句内第一个能量导数峰」当首字锚点。
在 1:20 处上一句「过」被拖成 3.2s 长音，**拖腔里的能量起伏被误当成新句起音**，
于是句 17/18/19 整句提前 2.5–3.6s。

**症状识别**：某几句的首字整齐地早 2–4s，且早的量级一致 → 一定是拖腔误判，
不是参数问题。**用官方 TTML 的逐字时间直接替换整条时间轴**，不要去调阈值。

### 6.2.5 融合规则：只修落静音的字，别逐字择优

**错误做法**：对每个字，在「官方时间」和「本地旧时间」之间选更贴起音的那个。

**为什么错**：本地旧版在 1:20 整句偏早 2.6s，但它**字与字的间距**恰好和起音分布对得上。
逐字择优会把官方字换成偏早的本地字 —— 句内节奏被撕裂：

```
官方  88.140 88.490 89.670 90.020 91.200 91.580
本地  85.380 86.344 87.528 88.544 89.686 90.112
择优后 88.03 88.47 87.53(本地!) ...   ← 字3 被拉到句首之前
```

**正确做法**（`realign_v10.py` 的规则）：

```
R0 骨架 = 官方 TTML 逐字 begin（d 由首尾字核对得出）
R1 句首字 → 吸附到「最近」的强起音（窗口 ±0.25s）
R2 句尾字 → 吸附到「最近」的强起音；拖腔尾音没有起音就保持官方值
R3 中间字 → 保持官方相对节奏；只有落进静音的字才推到最近发声段边界
R4 单调递增 + 最小间隔（约束最后生效）
```

要点：

- 吸附用**最近**的起音，不是「窗口内第一个/最后一个」。
  用「最后一个」当尾字会把拖腔尾巴提前 0.5–0.9s（实测拖腔尾音后面本来就没起音）。
- 吸附后如果字落进静音（强起音有时正好压在拖腔结束的静音边界上），
  再推到最近的发声段起点。

### 6.2.6 顺序：约束必须最后生效

v8 的顺序是「单调化+最小间隔 → 首尾重钉 → 单调化」，重钉把 `times[0]` 设成了
比 `times[1..7]` 都晚的值，随后的 `maximum.accumulate` 把句 27 的 9 个字
**压成同一时刻（6 字同刻）**。

**正确顺序**：`逐字择优 → 单调化+最小间隔 → 首尾重钉 → 重新夹紧约束`。
落地后必须再跑一次守门检查：

```python
# 同刻塌缩
if len(set(round(v, 2) for v in times)) < len(times): ...
# 异常大间隔
for u, v in zip(times, times[1:]):
    if v - u > 1.5: ...
```

### 6.2.7 验收判据：用发声段，不要用"到最近起音的距离"

**「到最近强起音的距离」有系统性偏差**：强起音只占音节的 40%（111 个 vs 294 字），
连音、拖腔里的字本来就远离任何起音，不代表字幕错位。

**硬判据是「字必须落在人声发声段内」**（F0 连续段 = 发声段）：

| 指标 | 定义 | 意义 |
|---|---|---|
| 落静音率 | 字的时间落在 F0 断裂里的比例 | 落静音的字字幕必定错位 |
| 跨静音处数 | 相邻两字之间隔着静音的处数 | 中间有字该移位 |
| 首尾字距起音 | 句首/尾字到最近强起音 | 用户主要看这个 |

《说好不哭》横向评测：

| 指标 | 能量峰版 | 混合版 | **官方骨架版** |
|---|---|---|---|
| 落静音字 | 6 / 294 | 7 / 294 | **0 / 294** |
| 相邻字跨静音 | 27 处 / 6.64s | 14 处 / 2.38s | **10 处 / 1.69s** |
| 同刻塌缩句 | — | 2 句 | **0** |

### 6.2.8 改时间轴不要碰排版

字幕的 `lines_sub.json` 里，`shot` 决定落位（top/bottom），**改时间轴时不要重跑落位判据**，
否则排版会变。正确做法是只更新 `times` / `start` / `end` / `cut` 四个时间字段，
保留已定稿的 `shot` / `y` / `x` / `fs` / `accent`。

同时必须核对 ASS：**样式行、文本、override 标签要一字不差，只有 Start/End 变**。
写个 diff 脚本逐条比，别靠眼看。

## 七、拆句规则（影响对齐上限）

- 单行上限 **12 字**，13 字以上均分两段
- 均分不是"按 12 硬切"，要**均分**（8+2 的畸形尾段很难看）
- 拆出来的两条是**两条独立记录**，时间首尾相接，不要合并

长句是 C 级的高发区：字越多，句内 DP 的自由度越大，越容易在拖腔处选错峰。

### 8.1 补充：官方 TTML 路线的额外检查项（2026-10-24）

### 8.2 拖腔导致的"整齐偏移"识别法

某几句的首字**整齐地早 2–4s，且早的量级一致** → 一定是拖腔误判（把拖长音里的
能量起伏当成了新句起音），不是参数问题。

**处理**：用官方 TTML 的逐字时间直接替换整条时间轴，**不要去调阈值**。
调阈值只会把偏差从"整句偏"变成"部分字偏"，更难查。

### 8.3 抓官方 TTML 的可用来源

```bash
# amll-ttml-db（GitHub，按 ISRC 或歌名检索）
# 文件结构：<歌名>.ttml，<body> 下 <p>（句）> <span>（字）
# 元数据在 <amll:meta>：qqMusicId / isrc / musicName / artists
```

拿到后先看 `<p>` 段数 vs 你的拆句数。**段数对不上是常态**（官方会合并短句），
走字符级 diff 对齐，不要按段号硬配。
