# 字幕对齐：只有一条流程，一套算法，一道硬门槛

> 字幕早半拍晚半拍，观众一眼就出戏。这一步决定成片"像不像专业剪的"。

**2026-10-22 重写**：原来的三套入口、两套参数已经合并。
不管手上是官方时间戳、歌词表还是烧好的 ASS，都走同一条链路、同一个算法、同一道 0.3s 门槛。

---

## 一、一条流程，三种输入

```
                  ┌─ 官方/TTS 时间戳（也要校准，不是免检）
song.m4a ──┐      ├─ 歌词表（只有文本 + 大致起止）
           ├──────┤
           │      └─ 已烧录的 ASS（只改 Start）
           ▼
   align_core.analyze()       ← 唯一前端：HPSS 去鼓 → 250–4200Hz → 4ms → 局部归一
           │
           ▼
   align_subs.py              ← 唯一入口：--lines 或 --ass
           │
           ├──▶ lines_sync.json / subs_sync.ass（校准结果）
           └──▶ sync_report.json（逐字偏差 + 置信度 + 门槛结论）
```

```bash
# A. 文本 → 逐字时间
python scripts/align_subs.py --audio song.m4a --lines out/lines.json \
    --out out/lines_sync.json --report out/sync_report.json --max-err 0.30 --strict

# B. 已烧录的 ASS → 只改 Start
python scripts/align_subs.py --audio song.m4a --ass out/subs.ass \
    --out out/subs_sync.ass --report out/sync_report.json --max-err 0.30 --strict
```

> **"有官方时间戳就不用校准"是错的。** 官方表也会整句晚 0.05–0.4s（实测过），
> 而且不同平台导出的表起点不一致。校准只花 8 秒，收益是把"差不多"变成"可测量"。
> 校准后 `delta` 就是"官方比实测晚/早多少"——超过 0.3s 的句子会被单独列出来。

## 二、唯一的一套算法（参数不许在别处再写一遍）

全部常量集中在 `scripts/align_core.py`，改那里等于改全链路。

| 环节 | 参数 | 为什么是它 |
|---|---|---|
| 采样 | 16 kHz 单声道 | 人声主区在 4kHz 以下，够了且快 |
| 帧 | NFFT 512 / HOP 64（**4ms**） | 10ms 步长会丢 1–2 帧的精度，字幕能感觉到 |
| 去鼓 | **HPSS**：频率方向中位 → 谐波 | 军鼓每一下都是强峰，不去掉会被当成字头 |
| 频带 | **250–4200 Hz** | 人声基频与共振峰都在内；再窄会丢辅音 |
| 变换 | `log1p(harm×12)` → 正向谱通量 | 压动态，让弱音节也能出峰 |
| 归一 | 1.5s 滑动中位相减 | 前奏与副歌的峰才可比，否则副歌永远赢 |
| 取峰 | 阈值 **0.10**、间隔 **45ms** | 实测这组在中文流行歌上最稳 |
| 对齐 | 句级位移搜索 ±0.6s + 句内 DP | DP 的转移代价必须含"间隔偏离惩罚" |
| 铺开 | 普通句 70%、大词句 52% | 剩下 30% 让整句立着，句末不拖 |

**为什么不再保留两套**：之前生成期用 250–3200Hz/10ms、修复期用 250–4200Hz/4ms，
同一句在两处会给出不同答案，而且没人知道哪个对。现在只有一套，误差来源也只剩一个。

## 三、硬门槛：逐字 ≤0.3s

`--max-err 0.30 --strict`：任何一个字超了，进程返回 2，不会静默过关。

### 0.3s 量的是什么（必须说清楚）

没有真值音频时，**"和标准答案的差"是测不出来的**。所以这里量两个东西：

| 指标 | 定义 | 用途 |
|---|---|---|
| `err`（门槛用） | 该字的时刻 → 本句**可信起音**的最近距离 | 判"有没有落在真实音节上" |
| `err_alt`（参考用） | DP 与贪心两套估计对同一个字的分歧 | 判"这个字到底对在哪个音上，是否含糊" |

- **可信起音**的阈值是自适应的：`0.55 × 本句中位峰强`。这首歌普通音节只有 0.15–0.25，
  用固定 0.30 会把正常字全判成错（实测过一次，30/36 句全红）。
- `err_alt > 0.3s` 的字进"人工复核队列"，但不判失败——它是"两种合理算法打架"，不是"一定错了"。

### 置信度分级

| 级别 | 条件 | 怎么处理 |
|---|---|---|
| **A** | `max_err ≤ 0.15` 且弱起音 ≤10% | 直接用 |
| **B** | `max_err ≤ 0.30` 且弱起音 ≤25% | 抽两帧听一下 |
| **C** | 超 0.30，或弱起音 >25% | **必须人工复核**，脚本会逐条列出 |

> ⚠️ **分层字幕（辉光层 + 实字层）只对齐实字层**，再把同样的位移套到另一层。
> 混在一起对齐会让两层分到不同的峰上（实测错到 1.22s，详见 `08-pitfalls.md` 第 24 条）。
> 而且这种错**能通过 0.3s 门槛**——每个字都落在起音上，只是落在了不同的起音。

### 本片实测（36 句 / 278 字，《无人知晓的我》）

```
偏差：中位 0.038s  p95 0.268s  最大 0.384s（门槛 0.30s）
两种方法分歧 >0.3s 的字：4 个（2 句）
A级 25 句 / C级 2 句 → 34/36 句过门槛
```

C 级两句：`那些欲言又止低头沉默`（0.304s）、`有些话不知道要怎么说`（0.384s）——
都是 10 字长句里的拖腔位置，**交给耳朵听，不要硬调参数**。

同一套算法跑已烧录的 ASS（568 字）：中位 0.000s、p95 0.273s、最大 0.284s，通过。

## 四、人工复核只有一件事：听那两句

脚本给不出"对/错"，只给"可疑"。C 级的处理流程：

1. 抽该句起止前后 0.5s 的音频，看波形/听一遍
2. 对照 `sync_report.json` 里逐字的 `t` 和 `peak`
3. 明显错的，直接改 `lines_sync.json` 里的 `times[]`（**改数据，不改脚本参数**）
4. 改完重跑 `align_subs` 只会覆盖正确的字——所以手动改过的句子要记在 `out/sync_manual.json`

**不要为了让它变绿去调阈值。** 门槛的作用是拦住不合格，不是逼你放水。

## 五、回流：校准结果要写回去

这是之前漏掉的一环——改完 ASS 就结束，`lines.json` 还是旧时间，下次重做又回到错的起点。

| 产物 | 用途 |
|---|---|
| `lines_sync.json` | **新的真源**：带 `times`/`start_fit`/`delta`/`win`/`grade`，下游 `make_subs` 直接吃 |
| `subs_sync.ass` | ASS 路线的结果，只改了 Start，其余字节原样 |
| `sync_report.json` | 逐字偏差 + 分级，出错时第一个看它 |

**规矩：一旦跑过 `align_subs`，后面所有步骤都引用 `lines_sync.json`，不再碰原始 `lines.json`。**
原始表只作为"输入记录"存档，便于追查 `delta` 是从哪来的。

## 六、唱歌 ≠ 说话（为什么不用 WhisperX 那类）

语音模型在唱歌上会退化，原因很具体：

- 基频大幅滑动（一个字跨五度），音素边界被拉糊
- 拖腔把字长拉 3–5 倍，模型没见过这种时长
- **伴奏压着人声**：鼓和贝斯在 250–3200Hz 有强能量，和辅音同频段

所以正确顺序永远是 `解码 → 去鼓（HPSS 或 Demucs）→ 只在人声上取峰`。
有 Demucs 更好：

```bash
python -m demucs --two-stems=vocals -n htdemucs -o out/stems song.m4a
# 之后把 --audio 换成 out/stems/htdemucs/song/vocals.wav
```

`align_core` 不检查你传的是不是人声轨——**这是调用方的责任**。传混音也能跑，
只是偏差会大一档（句起点标准差 0.415s vs 0.1s 量级）。

## 七、拆句规则（影响对齐上限）

- 单行上限 **12 字**，13 字以上均分两段
- 均分不是"按 12 硬切"，要**均分**（8+2 的畸形尾段很难看）
- 拆出来的两条是**两条独立记录**，时间首尾相接，不要合并

长句是 C 级的高发区：字越多，句内 DP 的自由度越大，越容易在拖腔处选错峰。
