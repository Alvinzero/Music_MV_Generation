# timeline.json 规范

> AI 只负责**生成和修改这个文件**，渲染器严格按它执行。
> 只要这个合同稳定，改字幕样式不用重出素材，换渲染后端也不用改剪辑逻辑。

## 1. 为什么用帧，不用秒

`0.35s @ 30fps = 10.5 帧`。四舍五入到 10 还是 11 都说得通，但一路累下去就是"字幕慢半拍"。

所以：

- **一切时间以整数帧存储**（`*_frame`）
- 秒只做**镜像字段**（`*_sec`），仅供人读，**不许参与计算**
- 换算只在一处发生：`frame = round(sec * fps)`，由 `timeline.py` 统一执行

## 2. 字段

```json
{
  "version": 1,
  "canvas": {"width": 1920, "height": 1080, "fps": 24},
  "duration_frames": 7009,
  "duration_sec": 292.042,
  "audio": {
    "music": "song.m4a",
    "voice": null,
    "loudnorm": {"I": -14, "TP": -1.0, "LRA": 11},
    "fade_in_sec": 1.0,
    "fade_out_sec": 2.6
  },
  "video": [
    {"id": "s01", "file": "clips/v01.mp4",
     "in_frame": 0, "out_frame": 144,
     "start_frame": 0, "start_sec": 0.0, "dur_sec": 6.0}
  ],
  "captions": [
    {"text": "这风铃 跟心动很接近",
     "start_frame": 251, "end_frame": 360,
     "chars": [{"c": "这", "f": 251}, {"c": "风", "f": 264}],
     "x": 960, "y": 946, "fs": 66, "accent": 0}
  ]
}
```

### video[]

| 字段 | 含义 |
|---|---|
| `file` | 素材路径 |
| `in_frame` / `out_frame` | **素材内部**取用区间（帧） |
| `start_frame` | 在**成片时间轴**上的起点（帧） |
| `xfade` | 与**前一镜**之间的转场：`{"type":"fade","frames":12}` |

三个坐标的关系：

```
start_{i+1} = start_i + (out_i - in_i) - xfade_i+1
```

`xfade` 记在**后一个镜头**上。`frames: 0` 表示硬切（用 concat）。

### captions[]

| 字段 | 含义 |
|---|---|
| `text` | 显示文本（可含空格作为停顿标记，渲染时忽略） |
| `start_frame` / `end_frame` | 整句显示区间 |
| `chars` | 逐字出现时刻，**每个字一个 f**，必须严格递增 |
| `x` / `y` | 整行长成后的**中心点**（不是左上角） |
| `fs` | 该句字号，允许逐句不同 |
| `accent` | 高亮字的下标，`-1` 关闭 |

## 3. 校验规则（`timeline.py check`）

**错误**（必须修）：

- 素材文件不存在
- `out_frame <= in_frame`
- 相邻镜头衔接不等于 `start_i + dur_i - xfade`
- 字幕 `end_frame <= start_frame`
- 字幕起点超出片长
- `chars` 时间不递增

**警告**（可接受但要知情）：

- 字幕重叠（两条的显示区间相交）
- 叠化帧数超过相邻镜头长度

## 4. 常见错误

| 症状 | 原因 |
|---|---|
| 字幕整体比画面慢半拍 | 某处用秒算了一遍再转帧，误差累积 |
| 转场处画面跳一下 | `xfade` 记在了前一个镜头上 |
| 尾段黑屏 1 秒 | 素材总长比音频短，没有用 `tpad` 补帧 |
| 声音比画面早结束 | 视频用了 `-t`，音频没跟同一个时长 |

## 5. 与动画 MV（本 skill）的衔接

本 skill 产出的是 `shots.json`（每镜 start/end 秒）。转成 timeline 时用：

```bash
python timeline.py build --cuts out/cuts.json --fps 24 --duration 292.01 \
    --audio song.m4a --lines out/lines.json -o out/timeline.json
```

`cuts.json` 就是 `[{"file":"clips/v01.mp4","start":0,"end":5.35}, ...]`（秒），
脚本负责按同一处换算成帧。

## 6. 前奏过长：>8 秒必须填信息（2026-10-26 数据回流）

**硬约束：音频是完整原曲，不二次剪辑、不缩短、不拆条。**
所以"前奏太长"**不能靠砍前奏解决**，只能靠"这段时间里放什么"。
所有"缩短片头 / 剪掉前奏 / 拆成几条"的建议一律不提。

### 6.1 先量出前奏有多长，别凭感觉

前奏 = `0 → 首句歌词的起点`。首句起点用**官方 TTML 首字**或 `lines_sync.json` 首句首字，
不要用 LRC 的句时间（那是参考值）。

```bash
# 有官方 TTML 时，第一段 <p> 的 begin 就是首句起点
python -c "import re,io; t=io.open('song.ttml',encoding='utf-8').read(); \
print(re.search(r'<p[^>]*begin=\"([^\"]+)\"', t).group(1))"
```

- 前奏 **≤8 秒**：正常处理，不用本节
- 前奏 **>8 秒**：必须按 6.2 填信息，并按 6.4 验收
- 前奏 **>20 秒**：属于高危区（本片 26.5 秒），三种填法至少用两种

### 6.2 三种填法（按成本从低到高，可叠加）

| 填法 | 具体做法 | 生成成本 | 适合 |
|---|---|---|---|
| **概念字** | 画面不动，只在合适位置压短句，每 5–6 秒换一句。例：「全程纸雕 · 没有一帧实拍」「XX 张纸，一座城」 | **0**（只改字幕层） | 任何片子，必做 |
| **成品预告** | 把正片里最强的 4–6 个镜头剪成 6–8 秒快剪放进前奏，相当于"先看成品" | **0**（素材已有，只改时间线顺序） | 前奏 >15 秒 |
| **制作过程快剪** | 材料铺开、搭建过程、手部特写——最有"这是真做的"的说服力 | 需新拍 / 新生成 | 手工/工艺类题材 |

**推荐组合：成品预告 + 概念字。** 前奏前 8 秒放成品预告快剪（最强镜轮播），
后段正常推进但配概念字。零新生成，纯时间线与字幕层操作。

概念字的写法约束：
- **说"这是什么"，不要说"请看到最后"**。观众要的是判断依据，不是请求
- 一句 ≤14 字，一次只讲一件事
- 不要写成歌词字幕的样式，避免观众误以为是歌词（可用不同位置/字号区分）

### 6.3 最强镜不许留到开唱

**前奏里必须出现全片最强的 1–2 个图形镜。**
这是纯时间线顺序调整，不需要新增生成。

本片反例：最有辨识度的「整墙窗格只有一扇亮着」排在 26 秒（开唱那一刻），
而 2 秒跳出已经决定了 60% 的人根本到不了那一秒。

操作注意：
- 前移的镜头在后面**仍然可以再用一次**（形成"预告 → 正片"的呼应），
  但两次出现要隔着足够距离，且第二次最好有不同的运镜或字幕，别像素材重复
- 如果前移会掏空后面的高潮，就**给前奏单独生成一个同主题的变体**，别硬拆

### 6.4 信息密度：每 5 秒必须有一次新信息

前奏区间按 5 秒切段，逐段问：**"这一段相比上一段，观众多知道了什么？"**

三种合格答案，任一即可：
1. **新画面**——换镜、换场景、换视角
2. **新字**——一句新的概念字/信息
3. **新动作**——同一场景里发生了明确变化（灯亮、窗开、物体移动）

**写不出答案的那一段就是要改的地方。** 这一条是可数、可验收的，不要靠"感觉还行"。

> **注意尺度不同，别读成冲突**：本节的「每 5 秒」只管**前奏区间**（观众还没决定要不要看）；
> 开唱之后进入正片，用的是 `12-douyin-narrative.md` 第四节的「每 15–25 秒一次有效变化」。
> 前奏密、正片缓，是有意为之。

### 6.5 反例存档（本片 0–26 秒）

| 时刻 | 实际内容 | 新信息 |
|---|---|---|
| 0–1s | 全黑淡入 | 无 |
| 1–6s | 静态歌名卡 | 只有"歌名"一条，且 6 秒不变 |
| 6–12s | 空房间 | 有换镜，但无人无字 |
| 12–18s | 静物 | 有换镜，信息增量极低 |
| 18–26s | 窗帘 + 纸城 | 第一次出现"城市"，太晚 |

整段 26 秒里，**有效的信息增量只有 3 次，且全部没有文字**。
按 6.4 的标准，至少应有 5 次，且第一次必须发生在第 0–3 秒。

## 7. 抖音双轨分镜字段（2026-10-26）

`timeline.json` 仍只以帧为计算真相。以下字段只保存**推流叙事与生成执行信息**，
不参与时长、叠化和字幕计算，渲染器忽略它们。完整规范见 `references/13-douyin-storyboard.md`。

### 7.1 在 `video[]` 的每个镜头上允许附加

| 字段 | 用途 |
|---|---|
| `traffic_role` | 推流任务：hook / world / goal / escalation / turn / payoff / breath / comment / series |
| `audience_question` | 观众此刻的疑问或期待 |
| `change_type` | new_info / new_relation / new_consequence / new_goal / breath / payoff |
| `visual` | 主体、动作、环境的一句话描述 |
| `camera` | 锁死、横移、前推、后拉等 |
| `continuity` | 与上一镜的空间、角色、光线和首尾帧关系 |
| `image_prompt` | 生图提示词 |
| `motion_prompt` | 图生视频运动提示词，只写运动 |
| `negative` | 负向词 |
| `backup_prompt` | 生成失败时的备选 |
| `acceptance` | 首末帧验收条目 |
| `repeat_of` / `upgrade` | 重复来源与本次升级，必须成对出现 |

### 7.2 字段写入与保留

- `timeline.py build --cuts` 会把 cuts 中这些字段原样保留到 `video[]`。
- 秒转帧只作用于 `start / end / start_frame / out_frame`，不重算叙事字段。
- `timeline.py check` 继续只检查文件、帧数、衔接和字幕；抖音字段由 `narrative_lint.py` 检查。
- 旧项目没有这些字段时仍可渲染；面向抖音的新项目必须在关3前补齐。

### 7.3 验收顺序

```bash
python scripts/narrative_lint.py out/shots.json
python scripts/narrative_lint.py out/shots.json --production
python scripts/timeline.py check out/timeline.json
```

先过叙事与生产检查，再进入渲染；不要用渲染通过代替叙事通过。
