# 抖音发布复盘：把数据变成下一版的修改任务

> 复盘只解决“下一版改什么”，不做无法验证的推流承诺。
> 使用创作者服务中心的真实数据；没有数据时只记录待补，不编造留存率。

---

## 一、发布后需要记录什么

| 数据 | 用途 |
|---|---|
| 播放量、点赞、评论、分享、收藏 | 看内容的基础反馈与传播意愿 |
| 前 3 秒/前 5 秒留存 | 判断首帧和开场是否有效 |
| 平均观看时长、完播率 | 判断长片留存，但不单独下结论 |
| 分段流失点 | 找到具体章节，而不是笼统说“节奏不好” |
| 主页访问、关注转化 | 判断系列识别与关注理由 |
| 评论原文与高频问题 | 提炼下一期选题、角色和互动方式 |

完整版与独立预告分开记录，不混用评价标准。

---

## 二、数据对应的修改方向

| 表现 | 优先检查 | 下一版动作 |
|---|---|---|
| 前 3 秒流失高 | 首帧是否慢、是否只有工艺或 Logo | 把异常、冲突或结果前置；重做首帧，不先改全片 |
| 前奏流失高 | 是否只有建城、材料展示 | 开唱前补世界规则和危机，前移最强图形镜 |
| 副歌前流失高 | 是否连续重复、没有新信息 | 提前换视角或给后果，压缩无变化段落 |
| 第二遍副歌流失高 | 是否只是第一遍重播 | 改人物关系、视角或后果，不换风格 |
| 点赞有、关注少 | 栏目和账号是否像一次性作品 | 固定期数、封面、角色和下一期承诺 |
| 播放有、评论少 | 问题是否太泛或太多 | 改成一个具体选择或记忆问题 |
| 收藏高、完播低 | 长视频本身的价值与长度 | 不直接判失败，继续看主页访问与关注 |
| 数据全面偏低 | 不能只看剪辑 | 回顾选题、首帧、封面、标题与对标是否错位 |

---

## 三、复盘流程

1. **先找最早的大流失点**：不要一上来改结尾。
2. **只改一个主变量**：首帧、封面、剧情速度、评论问题，分开判断。
3. **写成可执行问题**：不要写“节奏再快点”，要写“前 8 秒增加纸城遇雨规则”。
4. **回流到下一首**：更新 `douyin_brief.md`、L2-D 评分证据和分镜否决项。
5. **需要对标时再查榜单**：看同形态作品是否正在涨，不拿旧样本冒充当前趋势。

## 四、复盘记录模板

```json
{
  "work": "作品名/期数",
  "form": "full_song",
  "main_goal": "follow",
  "first_major_drop": "00:00-00:03",
  "evidence": "前3秒流失明显高于本账号近5期中位数",
  "single_change": "首帧从纸纤维微距改为纸城遇雨",
  "keep": ["纸雕材质", "男女角色位置", "完整原曲"],
  "next_episode_rule": "前奏必须先建立纸城怕雨，再展示建城过程",
  "data_missing": []
}
```

## 五、禁止的复盘方式

- 用单条作品就宣布“这个风格不行”
- 没有分段数据却断言“副歌不够炸”
- 把点赞当唯一目标，忽略收藏、评论和关注
- 为了数据好看，正片偷偷裁短却继续宣称完整原曲
- 把所有问题都归因于“平台不给流量”

---

## 六、先分清是分发问题还是留存问题

| 指标 | 它实际在量什么 | 不要被它误导成 |
|---|---|---|
| **播放量 / 同类中位** | 算法愿不愿意给你试探流量 | 内容好不好 |
| **2s 跳出率** | **第一眼**：首帧、第 0–3 秒的画面与字 | "没有旁白"（2 秒根本来不及听） |
| **5s 完播率** | 开头之后那一小段有没有持续信息 | 整体质量 |
| **完播率** | 时长与结构的综合结果，受前两项强烈影响 | 独立可优化的指标 |

> **播放量是诊断的前提，不是结论。**
> 播放量明显高于同类中位，说明算法已经给了试探流量，**分发端没有问题**。
> 此时所有精力都放在留存，不要去动标题、话题、发布时间。

**完播率低不要直接归因于"片太长"。** 本 skill 的硬约束是
**画幅固定 16:9、音频完整原曲不剪不拆**，片长不可变，"片太长"这个归因没有可操作性。
要往"中段信息密度"和"情绪曲线"上找，那里才有得改。

---

## 七、按指标定位到具体文档

| 数据表现 | 最可能的原因 | 去哪改 |
|---|---|---|
| **2s 跳出高，其他正常** | 首帧黑/近黑；前 3 秒是静态字牌；开场没有概念字 | `06-title-card.md` 第〇节；`quality_check.py` 首帧亮度门 |
| **2s 跳出高 + 5s 完播也低** | 上面那条，**加上**前奏段信息密度不足 | `04a-timeline.md` 第 6 节 |
| **2s 好，5s 开始掉** | 开场承诺了东西，但第 3–10 秒没兑现；好镜头全在后面 | `04a-timeline.md` 6.3 最强镜前移 |
| **2s、5s 都好，完播率低** | 中段没有第二个高潮 | `02-scoring.md` 情绪曲线；`12-douyin-narrative.md` 第四节 |
| **播放量本身就低** | 才是分发问题：封面、标题、发布时间 | `07b-cover-brief.md`、`11-copywriting.md` |
| **封面点击率低、进来的人留存好** | 封面问题，正片别动 | `07b-cover-brief.md` |

## 八、案例存档：《说好不哭》第一次数据回流（2026-10-26）

**数据**：播放 706（同类中位 47，**15 倍**）｜2s 跳出 59.94%（中位 39.14%）｜
5s 完播 15.77%（中位 46.39%）｜完播 0.97%（中位 4.80%）｜片长 3:42

**归因**：典型「2s 跳出高 + 5s 完播低」→ 首帧 + 前奏信息密度，**不是分发问题**。

**取证**（抽 0/1/2/3/5/6/8/12/18/24/26 秒共 11 帧，不凭记忆描述自己的片子）：

| 时刻 | 内容 | 判定 |
|---|---|---|
| 0s | 纯黑（淡入） | 首帧信息量为零 |
| 1–6s | 静态歌名卡 | 6 秒只有字在动 |
| 6s / 12s | 空房间 / 静物 | 无人无字 |
| 26s | 整墙窗格只有一扇亮着 | **最强镜，排在 26 秒** |

首句歌词 26.335s，官方 TTML 首字 26.510s → **26.5 秒前奏是原曲结构，不是字幕漏做**。

### 顺带发现的两个工程漏洞

- `quality_check.py` 的 `--ignore-head` 默认 1.6 秒，**把首帧黑帧亲手豁免了**，
  所以"质检通过"和"首帧全黑"同时成立。已加独立首帧亮度门。
- 钩子分评的是 L2 分镜第一镜，而片头后加、置顶，**评分对象 ≠ 交付对象**。
  已改为评交付文件第 0–3 秒；并要求**片头必须作为 s01 留在 `shots.json` 里**，
  这样 `narrative_lint.py` 的「首镜必须 hook」才管得住它。

### 一条反直觉的教训

**不要试图给"开头是否静止"写自动数值判定。**
实测静态字牌的帧间像素差（1.45–1.65）比正常慢推镜头（0.90–1.11）更高
（纸面纹理会闪），数值分不出"无聊的静止"和"好看的慢推"。
而首帧亮度的区分度极大（坏开头 0.02，六个正常镜头 49–62），所以只保留亮度门，
运动与钩子必须抽帧人看。
